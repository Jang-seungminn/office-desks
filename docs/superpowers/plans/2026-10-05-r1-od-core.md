# R1: od-core (Rust port of the native core) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a Rust crate `od-core` that reproduces the behavior of the Node core's native path, so that later milestones can serve the existing API from Rust. The Node core is `bridge/src/{model,stateMapper,screen,keys,hire,home,org,awards,stats,uploads,localImage,commands,answer,gitInfo,transcript,subagents}.ts` plus `bridge/src/native/*` and `bridge/src/backend/{types,native}.ts`.

**Architecture:**
- **Workspace.** A Cargo workspace lives at the repo root (`Cargo.toml` with `members = ["crates/*"]`) and holds the crate `crates/od-core`.
- **Spec.** The TypeScript source and its vitest tests are the spec. Each task ports one cohesive group of modules and their tests.
- **Golden fixtures.** A small TS script in `bridge/scripts/golden.ts` runs the real TS functions on fixed inputs. It writes their outputs as JSON to `crates/od-core/tests/golden/`. Rust tests assert byte-equal JSON, which keeps wire shapes identical.
- **No runtime changes.** The Node bridge is not modified, except for adding the golden script.

**Tech Stack:**
- Rust 1.94 (edition 2021), tokio 1, serde and serde_json 1, portable-pty 0.9, vt100 0.16, unicode-width 0.2, sha1 or sha2 (repo id), rand (tokens), base64, thiserror.
- Tests run on `cargo test`.
- The golden script runs on `tsx`.

**Spec:** `docs/superpowers/specs/2026-10-05-desktop-app-design.md` (milestone R1). The TS sources listed per task are the behavioral spec.

## Global Constraints

- **Platforms.** It must run on macOS and Windows. CI adds a `rust` job on `macos-latest` and `windows-latest` running `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test`. The existing npm job stays.
- **Wire shapes.** JSON must be identical to `bridge/src/model.ts`:
  - camelCase field names (`#[serde(rename_all = "camelCase")]`);
  - `null` for absent optional values, never omitted unless TS omits them;
  - numbers as JSON numbers, with timestamps in ms as `i64` or `f64` exactly like TS.

  Golden tests pin this.
- **Messages.** Korean user-facing messages and error codes must be identical to the TS ones. Copy them verbatim.
- **Processes.** No shell anywhere. Use `std::process::Command` or `tokio::process::Command` with argv. On Windows, `.cmd` shims follow the TS `resolveSpawn` and `unsafeForCmdShim` rules.
- **Async model.** The library is async (tokio). PtyHost uses a dedicated blocking reader thread per PTY and fans out output to subscribers.
- **Errors.** Use one `BackendError { code: String, message: String }` (with `thiserror`), mirroring `bridge/src/backend/types.ts`.
- **Tests.** Never spawn `claude` or touch the user's state. Use temp dirs (`tempfile`) for homes and repos. PTY tests spawn the **test binary itself** (`std::env::current_exe()`) with an env flag that makes it act as an echo program. That works the same on macOS and Windows.
- **Commits.** Messages are a subject, a blank line, then exactly:

  ```
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_013wdfUqZP1py6R116oZnY8V
  ```

  Use `git commit -F <file>`.
- **Process discipline.** Never start servers or agents in this milestone, never kill processes, never use port 4317, and never touch the user's repos or `~/.office-desks`.

## Review Focus

1. **JSON shapes and Korean messages.** They must be byte-identical to TS. Pinned by golden tests (Task 1 sets up the mechanism, and every task adds goldens).
2. **PTY behavior on Windows (ConPTY).** This covers spawn, write, resize and exit, plus the DA/DSR responder. Pinned by the CI windows job (Task 7).
3. **Claude hooks to state.** The mapping and the trust-dialog first-prompt flow must be identical to TS. Pinned in Tasks 6 and 9.
4. **git operations.** Worktree list, add and remove (no `--force`), changes and diff must match TS on real scratch repos, including Windows paths and 8.3 short names. Pinned in Tasks 4 and 5.
5. **Transcript parsing.** Claude and Codex JSONL must give identical conversation JSON, using the existing fixtures. Pinned in Task 8.

## Tasks

Every task follows the same steps:
1. Read the listed TS source and tests.
2. Add golden cases to `bridge/scripts/golden.ts` where the task says so, and regenerate them with `npx tsx bridge/scripts/golden.ts`.
3. Write the Rust tests first: the ported vitest cases plus golden comparisons. Watch them fail (RED).
4. Implement until they pass (GREEN).
5. Run `cargo fmt`, `cargo clippy -D warnings` and `cargo test`.
6. Commit.

Module names follow the TS files (`state_mapper.rs`, `screen.rs`, …). Export only what later milestones need, from `lib.rs`.

### Task 1: Workspace, CI job, model types, golden mechanism
- Create the root `Cargo.toml` workspace and `crates/od-core` (lib).
- Add `.gitignore` entries for `/target`.
- Add the CI job `rust` to `.github/workflows/ci.yml`, with a matrix of macos and windows: `dtolnay/rust-toolchain@stable` (with `rustfmt` and `clippy`), `Swatinem/rust-cache@v2`, then `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test`.
- Port `bridge/src/model.ts` to `model.rs`. Every exported interface and union becomes a serde struct or enum. `CharacterState` and similar string unions become enums with `#[serde(rename_all = "lowercase")]` or explicit renames that match the TS strings. `ServerMessage` becomes `#[serde(tag = "type")]` with the same variant names.
- Create `bridge/scripts/golden.ts`. It is a tsx script that writes `crates/od-core/tests/golden/*.json`. Start with a representative `OfficeSnapshot` (built by the TS `toSnapshot` from `bridge/test/fixtures/worktree-ps.json` and `terminal-list.json`) and each `ServerMessage` variant.
- Add a Rust test that deserializes each golden, re-serializes it, and asserts JSON equality as `serde_json::Value` after a key-order-insensitive comparison.
- Add the root script `"golden": "tsx bridge/scripts/golden.ts"` to `package.json`.

### Task 6: Claude hooks
- Port `native/hooks.ts`:
  - `HOOK_EVENTS`.
  - `hook_settings(relay_command: &[String])`. **Change from TS:** the relay is our own binary, `<office-desks exe> hook-relay`, not `node hook-relay.mjs`. Build each hook command string from the relay argv, quoted with forward slashes as the TS code does.
  - `HookState`, `initial_hook_state` and `apply_hook`, with exactly the TS transitions (permission and idle notifications, tool summaries, `since` handling).
- Add `hook_relay::run()`. It is a library function the binary will call: read stdin, POST to `OFFICE_DESKS_HOOK_URL` with a 2 s timeout and a 3 s overall exit timer, and always return exit code 0. Use a tiny blocking HTTP client (`ureq`) or raw TCP; no TLS is needed.
- Port the tests from `bridge/test/{hooks,hookRelay}.test.ts`. The relay test uses a local `TcpListener`.

### Task 7: PtyHost (portable-pty + vt100)
- Port `native/ptyHost.ts` as `pty_host.rs`. The API:
  - Lifecycle: `spawn(id, PtyOptions)`, `has`, `kill` and `dispose().await` (kills all, waits ≤ 2 s).
  - Input and screen: `write` (returns `terminal_not_writable` when the PTY is gone), `screen_lines`, `serialize`, `size`.
  - Output and events: `on_data(id) -> subscription` and `on_exit`. Use a `tokio::sync::broadcast` channel or a callback registry; the choice is yours, but unsubscribe must be explicit and leak-free.
  - Modes and state: `resize` (no-op when the size is the same, tolerant of errors), `set_replies(id, on)`, `cursor_hidden`, `modes` (bracketed paste, application cursor), `ids`.
  - Scrollback: `scroll_lines(id)` for scrollback access.
- Use `vt100::Parser::new(rows, cols, SCROLLBACK=1000)`. The reader thread feeds the parser (behind a mutex) and broadcasts the raw bytes.
- **Query responder.** vt100 doesn't answer terminal queries. While `replies` is on, scan output for:
  - DA1 (`ESC[c`, `ESC[0c`), replying `ESC[?1;2c`;
  - DSR cursor position (`ESC[6n`), replying `ESC[{row};{col}R` from the parser's cursor, 1-based;
  - DSR status (`ESC[5n`), replying `ESC[0n`.

  Write each reply back to the PTY. Handle sequences split across reads.
- **Windows.** Follow `resolveSpawn`: run `.cmd` shims via `cmd.exe /d /s /c "<quoted>"` and refuse cmd metacharacters. portable-pty's `CommandBuilder` takes args. Build the exact command line the TS code builds and pass it through the API that portable-pty offers for raw Windows command lines. If no such API exists, document how quoting is achieved and test the produced argv.
- **Tests.** The echo program is the test binary re-executed with `OD_TEST_ECHO=1`, which reads stdin and writes `got:<line>`. Cover:
  - screen lines, data subscription, unsubscribe, resize and size;
  - serialize replay equality (into a fresh `vt100::Parser`);
  - the DA/DSR responder (the echo program writes `ESC[6n`, reads the reply in raw mode and prints it);
  - the mute switch;
  - exit and kill;
  - `terminal_not_writable` after exit.
